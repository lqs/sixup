# 設定レシピ

<a href="recipes.md" lang="en">English</a> | <a href="recipes.zh.md" lang="zh-Hans">简体中文</a> | <strong>日本語</strong>

sixup は回線が何を提供しているかを自分で判断するので、ほとんどの場合、WAN と LAN のインターフェイスを指定するだけで動きます。

```sh
sudo sixup -wan eth0 -lan eth1
```

以下のレシピは、それを超える必要があるときのものです。表で目的を探し、その節でコマンドと変わる点を確認してください。どの例でも `eth0` が回線側、`eth1` と `eth2` が LAN のポートです。レシピは組み合わせられます。たとえばルーター上のリゾルバと NAT64 の両方を使うなら、両方のオプションを指定します。

| やりたいこと | オプション |
|---|---|
| [インターネットから LAN のホストに届くようにする](#インターネットから-lan-のホストに届くようにする) | `-unsolicited allow`、さらに閉じるなら `deny` |
| [複数の LAN セグメント](#複数の-lan-セグメント) | `-lan eth1:0 -lan eth2:1` |
| [SoftBank 光](#softbank-光) | `-wan-iid ::1111:1111:1111:1111` |
| [上流が通知しないプレフィックスを手動で指定する](#上流が通知しないプレフィックスを手動で指定する) | `-wan-prefix 2001:db8:100::/48` |
| [トンネルのファイアウォールルールを自分で管理する](#トンネルのファイアウォールルールを自分で管理する) | `-tunnel-nat off` |
| [ルーターのアドレスを固定する](#ルーターのアドレスを固定する) | `-wan-iid ::1 -lan-iid ::1` |
| [DNS サーバーを指定する](#dns-サーバーを指定する) | `-ra-dns self`、またはサーバーのアドレス |
| [DHCPv6 でアドレスを配布する](#dhcpv6-でアドレスを配布する) | `-dhcp6s-mode stateful` |
| [下流のルーター](#下流のルーター) | 上流のルーターに `-dhcp6s-mode stateless` |
| [IPv6 シングルスタックまたは IPv6-mostly の LAN](#ipv6-シングルスタックまたは-ipv6-mostly-の-lan) | `-nat64 jool` |

新しい回線では、まずドライランを実行してください。回線とやり取りして、回線が提供するものを表示し、システムは何も変更しません。

```sh
sudo sixup -wan eth0 -dry-run
```

## オプションが要らないもの

- **LAN のファイアウォール。** インターネット側から始まる接続は、LAN に届く前に破棄されます（RFC 6092）。LAN 自身の接続への応答は通り、過去 5 分以内に外へ送信した LAN のエンドポイントあての通信も通るので、Tailscale などの P2P プログラムはそのまま動きます。IPsec（AH、ESP、IKE）と HIP も RFC 6092 のとおり通します。ポートを開ける必要のあるプログラムは PCP で要求でき、IPv4 なら NAT-PMP でも要求できます。IPv4 では、トンネルのアドレスのポートもそのホストへ転送されます。
- **委任プレフィックス。** sixup は DHCPv6-PD で /56 を要求し、そのうち一つの /64 を LAN に置いて、内蔵の RA で広告します。委任プレフィックスの残りは unreachable ルートで受け止めるので、割り当てていない部分あての通信はここで破棄され、回線側へ戻ってループすることはありません。
- **/64 が一つだけの回線。** 委任がないときは、上流の RA の /64 を LAN に移します（RFC 7278）。イーサネットの WAN では、上流のルーターが LAN のアドレスを WAN のリンク上で解決しようとするので、sixup が WAN 側でそれらの近隣探索に代理で応答し、回線事業者に何を申し込めばよいかを警告で示します。
- **PPPoE。** PPP デバイスを WAN に指定します（`-wan ppp0`）。ポイントツーポイントの WAN にはアドレス解決がないので、共有する /64 に代理応答は要りません。RA がなければ、デフォルトルートはデバイスに向けます。
- **MAP-E。** DHCPv6 に MAP-E のオプションがあるとき、またはプレフィックスが日本の IPoE 事業者（v6プラス、BIGLOBE、OCN、NURO）のルール表に合うとき、sixup はトンネル `sixup-ipv4` を作り、共有 IPv4 アドレスを設定し、メトリックの大きい IPv4 デフォルトルートを追加します。さらに nftables のテーブル `inet sixup` で送信元ポートを回線のポートセットに収め、TCP MSS を調整します。
- **DS-Lite。** DHCPv6 が AFTR の名前を示すとき、sixup はそれを解決してトンネルを作ります。変換は AFTR が行うので、ここでは MSS の調整だけを設定します。
- **DHCPv6 が記述しないトンネル**（固定の 4in6 トンネルなど）。トンネルの通信が WAN に届くと、sixup はそれをキャプチャして両端のアドレスと IPv4 アドレスを推定します。

## インターネットから LAN のホストに届くようにする

既定では、LAN のホストにインターネットから届くのは、そのホストが PCP で要求したポートだけです。IPv6 本来の考え方のように、どのホストも自分のアドレスで届くようにしたいとき、たとえば各サーバーが自前のファイアウォールを持つネットワークでは、要求されていない通信も通します。

```sh
sudo sixup -wan eth0 -lan eth1 -unsolicited allow
```

プログラムからの要求さえ認めたくないとき、たとえばオフィスでは、PCP も止めます。外へ送信したエンドポイントにはしばらく届くので、P2P プログラムは引き続き接続できます。

```sh
sudo sixup -wan eth0 -lan eth1 -unsolicited deny
```

既定の設定は、家庭用ゲートウェイの簡易セキュリティを定めた RFC 6092 に従っています。家庭のネットワークには、誰も管理しておらず、インターネットに直接さらすつもりのない機器が多いので、その既定のモードでは LAN の誰も求めていない通信を破棄します。また、プログラムが着信を要求できるプロトコルを勧めており（REC-48）、PCP がそれにあたります。さらに、相手のアドレスによらないフィルタリング（REC-11、REC-17、REC-33）を勧めているので、ホストが使ったばかりのポートには誰でも届き、P2P プログラムは互いを見つけられます。家庭用ルーターの要件である RFC 7084 は、RFC 6092 への対応を求めていますが、既定の設定については定めていません（S-1）。RFC 6092 自身も開放したモードを既定にすることを認めており、それを簡単に選べることだけを求めています（REC-49）。それが `allow` です。

どの設定でも、フィルタするのは LAN へ転送する通信だけです。ルーター自身のサービスはご自身で守ってください。

## 複数の LAN セグメント

LAN のインターフェイスごとに、委任プレフィックスの中のサブネット番号を指定します。

```sh
sudo sixup -wan eth0 -lan eth1:0 -lan eth2:1
```

/64 が一つだけの回線では、一つのセグメントにしか足りません。サブネット 0 がそれを使い、ほかのセグメントにはグローバルプレフィックスがありません。セグメント同士で通信する必要があれば、ULA を設定します。

```sh
sudo sixup -wan eth0 -lan eth1:0 -lan eth2:1 -lan-ula auto
```

## SoftBank 光

SoftBank 光（ソフトバンク光）では、LAN のプレフィックスは RA または DHCPv6-PD から得ます。どちらになるかは、サービスの下にある NTT の回線によります。IPv4 は、DHCPv6 が記述しない 4in6 トンネルを通ります。ボーダーリレーはこのトンネルを、レンタルの光BBユニットが WAN で使うアドレスあてに送ります。sixup はその通信からトンネルを見つけますが、自分がそのアドレスを持っていないと近隣探索に応答しないので、トンネルは確立しません。`-wan-iid` で光BBユニットのインターフェイス ID を指定してください。1G のサービスでは、通常 `::1111:1111:1111:1111` です。違う場合は、光BBユニットの状態ページでアドレスを確認できるはずです。

```sh
sudo sixup -wan eth0 -wan-iid ::1111:1111:1111:1111 -lan eth1
```

これで sixup が光BBユニットの代わりになります。

## 上流が通知しないプレフィックスを手動で指定する

上流によっては、プレフィックスをルーターへルーティングしているのに、RA でも DHCPv6-PD でも知らせないことがあります。たとえば、契約により回線へ静的にルーティングされる固定プレフィックスや、VPS の /64 です。その場合は手動で指定します。

```sh
sudo sixup -wan eth0 -wan-prefix 2001:db8:100::/48 -lan eth1
```

このとき DHCPv6 クライアントは、DNS サーバーなどの設定だけを要求します。回線に RA がない場合、デフォルトルートは別の方法で設定してください。VPS では普通すでに設定されています。DHCPv6 も DNS サーバーを知らせないなら、`-ra-dns` で指定します。

VPS の /64 のような /64 は、RA から得たときと同じように LAN と共有します。ルーターは WAN にその中の /128 だけを持ち、LAN のホストに代わって WAN 側で近隣探索に応答します。それより短いプレフィックスは委任プレフィックスとして扱い、LAN のセグメントに分割し、下流のルーターにも委任します。

VPS の /64 を WireGuard 経由で自宅の LAN に使うには、WireGuard が近隣探索を運ばないので、その上に GRETAP トンネルを重ねます。VPS でこのコマンドを GRETAP デバイスを LAN として実行し、自宅でもそのデバイスを WAN として sixup を実行します。

## トンネルのファイアウォールルールを自分で管理する

MAP-E の回線で、既存のファイアウォールもトンネルから出る通信をマスカレードしていると、回線のポートセットの外の送信元ポートを割り当ててしまい、一部の接続しか通りません。sixup はそのようなチェーンを見つけると警告します。トンネルの送信元 NAT と MSS の調整を自分のルールに任せるには、この機能を止めます。

```sh
sudo sixup -wan eth0 -lan eth1 -tunnel-nat off
```

## コンテナの NAT66

Docker はコンテナに固定のアドレスを割り当てるので、変わるプレフィックスには追従できません。Docker のネットワークに ULA を割り当て、NAT66 を自分で行うのが現実的です。sixup は LAN インターフェイスから出る ULA を拒否しますが、ほかのインターフェイスから出る通信は送信元 NAT の後で確認します。自分の NAT が変換したものは出て行き、変換されずに ULA のまま出ようとするものは破棄されます。同じように、宛先 NAT で公開したポートにはインターネットから届きます。ルールを書いたのが Docker でも自分でも同じです。

```nft
table ip6 docker-nat {
    chain post {
        type nat hook postrouting priority srcnat; policy accept;
        oifname "eth0" ip6 saddr fd00:dead:beef::/48 masquerade
    }
}
```

## ルーターのアドレスを固定する

プレフィックスが変わってもインターフェイス ID が変わらなければ、ルーターを見つけやすくなります。WAN の最初のインターフェイス ID によるアドレスが、sixup が WAN アドレスとして報告するものです。

```sh
sudo sixup -wan eth0 -wan-iid ::1 -lan eth1 -lan-iid ::1
```

## DNS サーバーを指定する

既定では、LAN には上流が配布する DNS サーバーが渡ります。`-ra-dns` は RA と DHCPv6 サーバーでそれを置き換えます。項目は順に並べます。

ルーター上で動くリゾルバは `self` と書き、各 LAN でのルーターのアドレスになります。ULA を使えば、プレフィックスが変わってもそのアドレスは有効なままです。

```sh
sudo sixup -wan eth0 -lan eth1 -lan-ula auto -lan-iid ::1 -ra-dns self
```

LAN の別のホストで動くリゾルバは、そのアドレスで指定します。同じ理由で、そのホストには ULA の中の固定アドレスを与えてください。

```sh
sudo sixup -wan eth0 -lan eth1 -lan-ula fd12:3456:789a::/48 -ra-dns fd12:3456:789a::53
```

パブリック DNS もアドレスで指定します。

```sh
sudo sixup -wan eth0 -lan eth1 -ra-dns 2606:4700:4700::1111,2001:4860:4860::8888
```

項目は組み合わせられます。`-ra-dns self,upstream` はルーター自身のアドレスの後に上流のサーバーを加え、`-ra-dns off` は DNS を何も広告しません。

## DHCPv6 でアドレスを配布する

ホストにアドレスプールから、または固定のアドレスを割り当てたいときは、ステートフルな DHCPv6 サーバーを動かします。

```sh
sudo sixup -wan eth0 -lan eth1 -dhcp6s-mode stateful \
  -dhcp6s-static mac=aa:bb:cc:00:00:01,addr=::100
```

RA に M フラグが立つので、ホストは DHCPv6 にアドレスを求めます。`-dhcp6s-mode stateless` はアドレスを配布せず、DNS などのオプションと、下流のルーターへのプレフィックス委任だけを行います。

## 下流のルーター

DHCPv6 サーバーは、上流から委任されたプレフィックスのうち LAN のサブネットと重ならない部分を、下流のルーターに委任します。既定は /60 です。この sixup の下にもう一台 sixup を置いても、設定は要りません。

```sh
# 上流のルーター
sudo sixup -wan eth0 -lan eth1 -dhcp6s-mode stateless
# 下流のルーター（WAN を上流の LAN につなぐ）
sudo sixup -wan eth0 -lan eth1
```

下流のルーターは /56 を要求して /60 を受け取り、自分の LAN に分割します。そのためには、上流の委任プレフィックスが /64 より短い必要があります。/64 は LAN に使うと残りがないからです。`-dhcp6s-pd-len 0` で下流への委任を止めます。

上流のファイアウォールは委任したプレフィックスあての通信を通し、下流のルーター自身のファイアウォールに任せるので、下流のルーターで PCP により開けたポートにも外から届きます。

## IPv6 シングルスタックまたは IPv6-mostly の LAN

LAN は IPv6 だけで運用できます。IPv4 アドレスも DHCPv4 も要らず、二つのプロトコルを並行して保守する必要もありません。クライアントは NAT64 を通じて引き続き IPv4 のインターネットに届き、その IPv6 パケットはルーターで IPv4 に変換されます。IPv6 シングルスタックへの移行は、ネットワークが IPv6 のためにできる最も意味のあることの一つです。そうしたネットワークが一つ増えるたびに、誰かが IPv4 を残し続ける理由が一つ減るからです。そうするつもりなら、この節はあなたのためのものです。

Jool のモジュールをインストールし、NAT64 を有効にして sixup を起動します。モジュールが読み込まれていなければ、sixup が `/sbin/modprobe jool` で読み込みます。

```sh
sudo sixup -wan eth0 -lan eth1 -nat64 jool
```

Jool は veth `sixup-nat64` の向こうの専用のネットワーク名前空間で動き、`64:ff9b::/96` を LAN とルーター自身のために変換します。変換している間、RA はそのプレフィックスを広告します（PREF64、RFC 8781）。変換後の IPv4 は、ルーターの IPv4 ルートに従って出ていきます。MAP-E のトンネルを通るときはほかの通信と回線のポートセットを共有し、トンネルがなければ設定済みのほかの IPv4 の出口を使います。ファイアウォールは `sixup-nat64` を通る通信を許可する必要があります。

クライアントが IPv4 に届く方法は二つあります。

- **クライアント上の CLAT**（464XLAT、RFC 6877）は RA からプレフィックスを得て、クライアント自身の IPv4 通信を変換するので、IPv4 アドレスを直接使うものを含め、どのアプリケーションも動きます。
- **DNS64** は、IPv4 しかない名前に、そのプレフィックスの中のアドレスを答えます。お好みのリゾルバが必要で、sixup は提供しません。IPv4 アドレスへ直接接続するアプリケーションには効きません。

RA の PREF64 に従って CLAT を有効にする組み込みの対応状況です。執筆時点で分かっている範囲のものです。動きが速いので、各ベンダーの最新情報を確認してください。

| システム | CLAT |
|---|---|
| iOS、iPadOS 16 以降、macOS 13 以降 | 組み込み。ネットワークに IPv4 がないときに有効になります |
| Android 11 以降 | 組み込み。モバイルネットワーク向けの CLAT はずっと前からあります |
| Windows 11 | Insider Canary ビルド 29599 から[パブリックプレビュー](https://techcommunity.microsoft.com/blog/networkingblog/announcing-windows-clat-public-preview/4506046)。既定では無効で、`netsh interface clat set global permit=enabled pref64fromra=enabled` で有効にします。SLAAC が必要なので、`-ra-slaac=false` とは組み合わせられません |
| Linux | 組み込みの対応はなく、clatd のような CLAT デーモンが必要です |

ネットワークから一度に IPv4 をなくす必要はありません。IPv6-mostly のネットワークでは、IPv4 が必要なクライアントには IPv4 を残し、ほかのクライアントは使いません。DHCPv4 サーバーがオプション 108、IPv6-Only Preferred（RFC 8925）を送ると、対応するクライアントは IPv4 アドレスを手放し、代わりに NAT64 を使います。sixup は DHCPv4 を動かさないので、このオプションはお使いの DHCPv4 サーバーで設定してください。

NAT64 を通してプライベートな IPv4 アドレスに届くには、ネットワーク固有のプレフィックスを使います。Well-Known Prefix ではプライベートアドレスを扱えない場合があるからです（RFC 6052）。

```sh
sudo sixup -wan eth0 -lan eth1 -nat64 jool -nat64-prefix fd00:64::/96
```

クライアントに CLAT を有効にさせず、DNS64 だけで NAT64 を提供するには、プレフィックスを RA に載せないようにします。

```sh
sudo sixup -wan eth0 -lan eth1 -nat64 jool -ra-pref64 off
```
